Triangulator wire formats - animated tour

How the sampler's samples travel over UDP to the collector: four datagram kinds, how big samples are split into parts, and how bytes are encoded and decoded. Source of truth: common/wire.hpp, common/resource_wire.hpp, common/memory_wire.hpp, socket_sampler/protocol.hpp, collector/protocol.hpp, collector/ingest.hpp.

1. Big picture: one UDP port, four datagram kinds

Everything flows one way (sampler → collector, no acks, no retransmission). The first 4 bytes of every datagram - the magic - say which kind it is. Big samples are split into parts that the collector puts back together. Timings are compressed; click a packet to drop it, or raise packet loss and watch a sample arrive with a hole.

Every datagram stays ≤ 1400 bytes, so it fits one 1500-byte Ethernet MTU: no IP fragmentation. "Parts" and "chunks" are the protocol's own splitting, done by the sampler, not by the network.

2. TMON: one tick, many chunks

A tick is one snapshot of every thread of the target. Each datagram holds a 48-byte header + at most 10 thread records (112 B each). With more threads the sampler sends chunks = ceil(threads / 10) datagrams that share the same header (same sequence, session, clocks) and differ only in chunk.

What the collector does with each chunk (Monitor::Accept / Drain)

  1. Decode: length = 48 + 112×records, magic + version, chunk < chunks, interval 100-5000 ms, thread ids valid and unique.
  2. Find the pending tick by sequence; first chunk creates it. Later chunks must match with SameTick() (all header fields but chunk) or count as bad.
  3. Duplicate chunk? already in chunks_seen_ → counted and ignored.
  4. Wait a grace period max(0.25 s, min(2 s, 2×interval)) for stragglers, then Drain: records are sorted by (chunk, arrival) and processed, oldest tick first.
  5. Loss estimate: expected = chunks × (skipped sequences + 1), seen = chunk count; the difference feeds the dashboard's packet-loss health. A tick with missing chunks is still used.

3. Byte layouts

All integers are little-endian, structs have no padding (enforced by static_asserts), strings are NUL-padded fixed arrays. Hover a byte or a row.

4. TRES and TVMA: one sample = several "parts"

Slow-rate samples are built from part 0 = summary (fixed-size array of u64 values) and parts 1.. = rows (sockets or memory regions). Every part carries the same 64-byte header (session, sequence, clocks, pid, parts) plus its own part number and count.

Region parts are only sent when the layout changed (or on a periodic refresh); otherwise the summary alone is sent and the collector keeps its layout. Every region part except the last must be full (20 rows) because the collector places part N at row (N-1)×20.

Reassembly on the collector

  • Parts are placed by part number into a per-sample assembly keyed by sequence; order of arrival does not matter.
  • A newer sequence arriving while an older sample is incomplete finishes the old one: missing socket parts → sample kept, sockets_complete = false; missing summary → discarded, counted incomplete.
  • Older sequences than the published one are late; same sequence with different header fields is bad_parts.
  • session is shared with TMON, so the dashboard can match all streams from one sampler run.

5. Encode → send → receive → decode

There is no serializer. The wire struct is the format: the sampler fills a struct and sends its bytes; the collector copies bytes back into the same struct and validates. Step through the TMON path.
